# Android 提醒补全与可靠性修复

日期：2026-10-23。基于 v1.1.7 工作树。本次范围为 Android 提醒分发、设置诊断和模拟器回归；不改变服务端事件规则。

## 已定位的代码问题与修改

| 问题 | 修改后的行为 |
| --- | --- |
| “检查真实提醒链路”启动异步工作后立即返回，页面读到旧状态；并发检查直接丢弃等待者 | 原生回调等待检查完成，并发请求合并到同一轮；页面显示检查中、禁用重复操作并捕获错误 |
| 领取事件后权限／渠道变化，可能将没有发出的事件永久记为已提醒 | 提交通知前再次检查；明确未发送时释放服务端领取记录，清除本地标记 |
| 明确未发送，但释放请求遇到断网；后续没有恢复路径 | 先持久化待释放批次；下一轮先幂等释放，再重新获取当前有效事件；不盲目重放旧消息 |
| 401 取消任务后，生命周期回调又重新注册 | 持久化授权暂停状态；成功配置新后台凭据后恢复调度 |
| 缓存下载失败覆盖了真实提醒检查结果 | 缓存错误独立显示，保留通知提交／权限／免打扰等结果 |
| 本机测试仅检查应用总通知权限，渠道关闭仍可能误报成功 | 同时检查具体渠道是否关闭；仍明确区分系统提交与横幅可见 |
| 提醒配置缺少明确引导 | 显示系统免打扰、主手机、通知权限、后台运行及小米悬浮／锁屏通知排查提示 |

保留现有渠道及用户的渠道重要性，不通过创建新渠道绕过关闭设置；保留同一语义事件一次、账户级 30 分钟间隔和免打扰规则。

## 验证方法与结果

Flutter 静态检查无问题；现有 27 项测试通过，2 项需要真实集成账号的测试跳过。

原生验收脚本位于 `scripts/android-reminder-probe/`，运行入口为 `scripts/Test-Android-Reminder-Dispatcher.ps1`。脚本调用 debug APK 的实际原生 `BackgroundSync`，进程内拦截 HTTPS，使用合成事件；不访问真实服务器、不向真实账号发送提醒。

Android API 34 模拟器的 7 个原生场景全部通过：

| 场景 | 实际结果 |
| --- | --- |
| 正常分发并故意令分析缓存失败 | 领取 1 次、系统活跃通知存在；第二轮不重复领取 |
| 应用免打扰 | 领取 0 次 |
| 确定未发送后，首次释放网络失败 | 释放共尝试 2 次，恢复后发送一次，重复检查不重发 |
| 两个并发手动检查 | 两个回调均等到同一轮完成，领取 1 次 |
| 后台授权 401 | 生命周期重新注册被阻止，不再请求提醒 |
| 系统通知权限拒绝 | 领取 0 次，保留权限拒绝原因 |
| 领取过程中通知渠道关闭 | 领取 1 次、释放 1 次，没有提交／本地已展示标记 |

原始结果保存于 `.runtime/android-reminder-probe/{normal,quiet,release_retry,join,auth,denied,channel_race}.txt`。
通过 computer-use 查看通知栏，实际看到了合成提醒。瞬时横幅没有完成可靠的视觉确认，因此不作为已通过项。模拟器旧快照启动时曾出现桌面及 System UI 无响应，改为冷启动后再运行测试；没有清除应用数据。

最后的 `channel_race` 用例会把测试模拟器的通知渠道关闭，`auth` 会取消其后台任务；不能直接将该测试后的模拟器配置当作用户安装默认值。

## v1.1.9：应用打开时仍漏提醒的修复

用户进一步确认，漏提醒发生在“应用开着”时。本轮沿前台链路定位出两处具体问题：

1. `main.dart` 的周期和恢复检查都嵌套在 `engine != null && !busy` 下，便笺／数据同步繁忙时，提醒检查也被跳过。
2. Android 分支直接返回原生通知路径，未使用原有 Flutter 应用内提醒对话框。因此系统未显示横幅时，前台没有独立可见提示。

修改后，前台提醒使用独立的 15 秒调度器，恢复应用和登录后立即检查；并发检查合并，失败释放执行槽并在下轮重试。暂停或销毁页面后停止前台计时。前台原生检查不再等待两份分析缓存下载，数据仍由 Flutter 自身刷新。

原生分发器在同一次服务端领取中选择一个展示位置：已恢复的应用窗口内显示对话框，否则使用系统通知。应用内已展示时不再重复发系统通知；窗口失效、退到后台或 UI 等待超时均能回退，超时后迟到的 UI 回调不能再额外弹窗。退出／切换账号、关闭提醒及页面暂停会清除应用内窗口。保留主手机、有效事件、应用免打扰、系统通知权限与渠道关闭、语义去重和 30 分钟间隔；系统免打扰开启时不使用应用内弹窗打断。

Flutter 静态检查通过，31 项测试通过、2 项真实账号集成测试跳过。新增 4 项调度回归覆盖独立轮询、检查期间的合并、失败恢复及生命周期停止／恢复。原生弹窗通过 debug 专用 Activity 调用与正式包相同的展示器验收，该测试 Activity 不进入 release APK。

## 仍然存在的边界

- 当前仍为系统周期轮询，没有 FCM／厂商实时推送。系统调度、离线、省电、休眠和强制停止可能造成延迟，不能承诺及时弹出。[Android JobInfo 官方说明](https://developer.android.com/reference/android/app/job/JobInfo.Builder)。
- 高重要性渠道只是横幅条件之一，系统设置仍决定实际展示。[Android 通知官方说明](https://developer.android.com/develop/ui/views/notifications/time-sensitive)。
- 模拟器的原生分发成功不能证明用户小米／HyperOS 真机的后台送达可靠性，也不能证明服务端整条链路及时。
- 通知提交与本地／服务器存储无法组成单一事务。提交状态不确定的崩溃仍保持“不自动重发”的原有取舍；本次只恢复确定未发送的失败。
- 领取响应丢失、设备在领取后被杀死等不确定情形，尚未实现服务端可恢复投递协议；不能声称所有漏提醒已解决。
