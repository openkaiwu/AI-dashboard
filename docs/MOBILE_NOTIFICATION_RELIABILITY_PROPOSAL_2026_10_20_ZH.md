# 手机不主动弹出提醒：排查与解决方案（待实施）

日期：2026-10-20。范围：当前 Android 手机端及电脑 → 服务器 → 手机链路。此次仅审查代码、核对平台资料并编写文档，未修改程序、手机设置或服务器，未构建或发布安装包。

本方案与 [提醒逻辑优化方案](REMINDER_POLICY_PROPOSAL_2026_10_20_ZH.md) 配套：桌面默认静默、手机主动提醒、同一语义事件只展示一次、快速消耗须在建议的 15 分钟内严格超过 5 个百分点。提高送达可靠性不能通过放宽去重、缩短限频或反复重发实现。

## 1. 结论

当前手机采用“后台定期拉取后发布本地通知”，不是服务器实时推送。单纯提高通知优先级或增加一个权限按钮，不能解决后台任务未执行、电脑未上传、授权失效和接口阻断。

建议分两阶段实施：首先修复现有链路、增加可诊断状态；然后增加服务器事件推送，以周期同步作为补漏。必须用用户实际手机验收，不能继续把模拟器成功通知视为真机可靠性证明。

本次没有连接用户手机，也未读取线上送达日志。下文区分已确认的代码行为与待现场验证的原因，不能据此断言用户每次漏提醒都是某一个权限问题。

## 2. 先区分“不弹出”的具体阶段

完整链路为：电脑有效采集 → 用户允许的同步上传 → 服务端确认提醒事件 → 手机收到事件 → 通过去重、有效期和限频检查 → 提交 Android 通知 → 系统决定横幅／锁屏展示。

| 用户现象 | 优先检查 | 不应直接认定 |
| --- | --- | --- |
| 手机额度数据一直旧 | 电脑采集、上传设置与最近成功上传时间、账号对应关系 | 不能先归因于通知权限 |
| 打开应用才更新、才有提醒 | 后台任务实际执行、授权、后台网络限制 | “任务已注册”不等于“任务执行正常” |
| 通知栏有记录，但没有横幅或声音 | 具体通知渠道的重要性、声音、免打扰、系统设置 | 不能把该事件自动重发当作修复 |
| 本地测试通知成功，但真实提醒没有 | 服务端是否生成事件、有效期、去重／限频原因、后台请求结果 | 本地测试未覆盖服务器与后台链路 |
| 正常用几天后停止 | 任务停调度、后台授权／关联会话、网络、同步错误 | 不能简单要求永久常驻后台 |
| 只有旧提醒不再出现 | 已提醒记录、已读／忽略、风险解除 | 这可能是正确去重，不属于漏提醒 |

## 3. 当前代码确认的问题与风险

### 3.1 周期调度无法保证及时提醒

`apps/mobile/android/app/src/main/kotlin/dev/aihub/aihub_mobile/BackgroundSyncJob.kt` 使用 `JobScheduler.setPeriodic(15*60*1000L)`，要求网络可用并持久化任务。本次查看的移动依赖、Manifest 和后台实现未发现已接入的 FCM／厂商消息推送链路。

Android 周期任务受系统约束、Doze 和省电策略影响，注册成功不代表每 15 分钟准点执行。因此后台拉取容易错过短时风险，改成更短的定时器也不能根治。[JobInfo 官方说明](https://developer.android.com/reference/android/app/job/JobInfo.Builder)、[Doze 与 App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)。

### 3.2 非必要的分析下载会阻断通知

当前原生 `run()` 顺序为：获取 `/overview` → 保存缓存 → 获取 `/local-data` → 保存缓存 → 更新 `last_sync` → 检查通知候选。

因此即使 overview 已包含有效提醒，只要消耗分析接口失败、超时或缓存落盘失败，本轮就可能退出，根本没有进入通知发布。这是明确的代码依赖风险；是否正是用户现场原因需要日志确认。

解决：提醒获取与必要状态持久化构成独立高优先级流程；消耗分析缓存使用独立任务／独立错误状态。分析失败不能阻止已验证的新提醒，提醒失败也不能伪装成整体同步成功。

### 3.3 当前状态会高估“可以弹出”

- `BackgroundSync.status()` 在通知渠道不存在时也返回 `heads_up=true`。
- `BackgroundSettings` 将该值显示为“可弹出”；开关请求通知权限后仍可继续启用后台任务，没有把“同步开启”和“通知未授权”清楚区分。
- `LocalNotifications.showReminder()` 主要检查应用级通知授权；插件调用返回成功即返回 true，不等于横幅实际出现。
- 原生流程只拦截渠道 `IMPORTANCE_NONE`。渠道被用户改成较低级别时，通知可以进入通知栏而不弹横幅。
- 当前“后台运行与电池设置”实际跳转的是应用详情页，不保证直接定位到厂商自启动或后台运行设置。

Android 13+ 的通知运行时权限、Android 8+ 的渠道设置是不同条件；渠道创建后不能靠重复设置高重要性覆盖用户选择。[通知权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission)、[通知渠道](https://developer.android.com/develop/ui/compose/notifications/channels)。

解决：将状态改为“未授权／渠道未创建／渠道关闭／仅通知栏／具备横幅条件／系统设置需确认”。不要承诺“可弹出”；免打扰、锁屏和厂商策略仍可能影响实际展示。不通过频繁创建新渠道绕过用户设置。

### 3.4 后台授权可能静默失效

`server/internal/auth/background.go` 发放有效期 30 天的独立凭据，同时校验设备未撤销、账户有效且存在尚未过期的有效会话。后台可用期限不只取决于这 30 天。

`apps/mobile/lib/background_sync.dart` 仅在调用 `renew()` 时检查临近到期并换取凭据；`main.dart` 当前加载账号时调用它，且将异常吞掉。原生任务遇到 401 记录错误并重试，无法自行恢复有效授权。

解决：每次前台恢复与账号恢复时执行授权健康检查，错误可见；401 与网络错误分开处理，401 停止无效密集重试，明确显示“需重新登录／启用”。如需长期无人打开应用也能运作，应设计受限、可撤销的后台凭据轮换，校验设备和账户撤销状态；不能简单把令牌改成永久有效，也不能令注销后的后台继续取数。

### 3.5 数据同步与新鲜度是另外两个门槛

电脑默认只保存在本地，`apps/desktop/runtime.cjs` 在开启 `auto_sync` 后才进行自动同步。手机的“后台同步开启”不会自动让电脑上传新额度。

手机还检查 overview 生成时间是否超过 60 秒；服务端 `server/internal/codex/advisor.go` 对超过 11 分钟的采集样本不生成当前风险建议。前者是响应时间，后者是源数据时间，两者必须分别展示。持续上传时，15 分钟拉取不必然遇到旧数据；但上传停止或只手动同步一次后，手机即使成功访问服务器，也可能没有新鲜风险可提醒。

解决：提供显式的“同步到手机并提醒”开通流程，保持默认本地保存；用户开启后同步必要的额度摘要、事件与送达状态。显示电脑最后采集、最后上传、服务端最后接收、手机最后拉取四个时间。不能以刷新 overview 的生成时间掩盖源数据陈旧。

### 3.6 前后台切换和失败原因需要可追踪

原生流程发现 `foreground=true` 会让出通知，由 Flutter 前台逻辑承担展示。这种分工本身合理，但切换瞬间、Flutter 加载失败、账号切换时是否遗漏，需要并发测试，而不能仅靠一个布尔值推定“另一路已经处理”。当前只有单一 `last_sync` 和 `error`，不足以定位这一类问题。

解决：两端进入同一个原子事件分发入口；让出执行权不等于标记已提醒，只有实际完成所选展示流程才提交相应记录。候选被跳过时必须记原因。

## 4. 第一阶段：修好现有流程并让问题可诊断

### 4.1 最小修复顺序

1. 通知处理从消耗分析下载中解耦；设置独立超时、错误记录和重试策略。
2. 加入后台凭据、应用权限、渠道设置、后台任务最近执行与源数据新鲜度检查；不再把“已注册”“API 调用成功”当作完整送达成功。
3. 补充应用启动、恢复前台、登录恢复、设备重启后的任务健康检查。任务缺失时在授权仍有效的前提下幂等恢复，不重放已提醒事件。
4. 前台与后台使用相同语义事件键、送达记录和固定通知 ID；落实上一份方案的一次性提醒。
5. 添加两种明确分开的测试：本地系统通知测试；电脑／服务器 → 目标手机的端到端测试。测试事件使用专门类型，不影响真实额度提醒状态。

### 4.2 诊断信息与状态页

建议保留本地最近 7 天的结构化诊断记录，允许用户手动导出；服务端保存必要送达回执。不得记录登录令牌、会话正文或完整私人内容。

每次链路记录关联的 `event_id`／`trace_id`，至少包含：

- 源数据采集、上传、事件生成、后台任务开始／结束、手机接收、系统通知提交时间。
- 账号与目标设备的匿名标识、客户端版本、Android 版本、网络类型。
- 通知授权、渠道重要性、后台授权有效性、任务注册及最近实际运行状态。
- 跳过原因：`duplicate`、`quiet_hours`、`rate_limited`、`expired_event`、`stale_source`、`permission_denied`、`channel_blocked`、`auth_expired`、`network_error`、`foreground_handoff`、`analysis_sync_failed`。

状态页用用户能理解的描述，例如“电脑 18 分钟未上传”“已进入通知栏，横幅条件未满足”“本事件已提醒，未重复发送”，避免只显示一个绿色“已开启”。诊断不是新的弹窗来源。

### 4.3 区分三个成功状态

`received`：手机已收到事件。

`notification_submitted`：已调用系统通知发布接口，必要时核对系统活跃通知记录。

`opened`：用户点击了通知或在应用里查看事件。

不能把 `notification_submitted` 命名为“用户已看到横幅”。系统活跃通知记录也不能证明横幅真实出现；真实展示需要现场观察。用户没有点击不构成重复发送理由。

## 5. 第二阶段：推送作为主通道，轮询作为补漏

建议流程：

```text
电脑本地采集与分析
  → 用户允许后上传额度摘要／稳定事件
  → 服务端校验规则、去重、有效期、主提醒手机
  → 持久化事件与发送任务
  → 推送通道
  → 手机统一分发入口
  → 去重／限频检查
  → 一次系统通知 + 送达回执

周期后台任务 → 补拉尚未确认且仍有效的事件 → 同一分发入口
```

服务端事件创建应由新数据入库／事件上传触发，而不能继续只依赖手机请求 overview 时临时计算。推送任务与事件写入采用事务性 outbox，失败可恢复；发送重试使用同一事件 ID，不生成新的“提醒次数”。

### 5.1 推送通道选择

支持 Google Play 服务且网络可达的 Android 环境可以评估 FCM；需要时效的用户可见通知可使用适当高优先级，但它仍不是必达承诺，也不能拿来频繁同步后台分析。[FCM 消息优先级](https://firebase.google.com/docs/cloud-messaging/android-message-priority)。

对用户实际使用的国内手机，应先确认品牌、系统版本、Google 服务与推送网络可用性，再评估对应厂商推送或聚合 SDK；不能预先承诺只接 FCM 就覆盖所有手机。厂商接入需要包名、签名证书、开发者资质及推送配置的实际核验。本次没有选择供应商或创建外部账号。

如果平台自动展示通知消息，应用又自行发布本地通知，会增加重复风险。实施时必须按所选通道定义唯一展示负责人：能通过客户端统一入口的消息由客户端去重展示；平台托管展示的通道需定义固定标识、替换行为和回执对账，单独实测，不能宣称两者天然共享原子去重。

不使用“后台强拉起页面”“全屏覆盖”“高频精确闹钟”来模拟普通额度提醒；不把持续前台服务和常驻通知作为默认补丁。用户明确需要的低延迟应通过适合的平台推送链路解决。

### 5.2 有效期、重试与去重

- 快速消耗事件按前一方案设短有效期；过期只进入历史，不在用户几小时后联网时突然弹出。
- 偏低／耗尽事件恢复网络后重新检查当前风险，再决定是否需要首次展示。
- 推送和轮询携带同一语义事件 ID，前后台并发只允许一个路径展示。
- 网关接受消息不等于手机收到。没有回执时允许有限退避重试／补拉，但不得更换事件 ID 或连续提醒。
- 系统通知和数据库不能组成同一个事务。“绝不重复”与“所有崩溃都不漏”无法同时绝对保证。延续上一方案的低打扰取舍：发送状态不确定时保留列表记录，不自动生成第二次强提醒；必须记录这一状态以便排查。
- 多台手机默认指定一台主提醒设备；更换主设备不补弹已送达事件。手机不可达时不回退到桌面弹窗。

## 6. 用户设置流程

建议设置中提供一个“手机提醒检查”入口，依次检查：

1. 电脑和手机是否属于同一服务器与账号，电脑是否明确开启必要同步。
2. 是否指定本机为主提醒手机，后台授权是否有效。
3. 应用通知权限、额度通知渠道、横幅、声音和锁屏设置。
4. 后台数据、自启动和电池限制；根据实际品牌提供可验证的设置引导，跳转失败时给出手动路径。
5. 本地通知测试：让用户选择“看到了横幅／只有通知栏／没有收到”，不能只靠接口返回自动判为通过。
6. 退到后台后进行端到端测试；显示消息经过各阶段的结果，而不是要求用户一直打开应用等待。

系统免打扰、用户强制停止以及设备离线等情况下，不承诺即时横幅。应用应尊重用户设置；强制停止后的恢复能力必须按真实平台测试并明确说明，不能视为普通进程回收。

| 范围 | 主要文件／模块 | 计划变化 |
| --- | --- | --- |
| 原生 Android | `BackgroundSyncJob.kt`、`MainActivity.kt` | 解耦分析任务、统一分发、正确状态检测、诊断与任务恢复 |
| Flutter | `background_sync.dart`、`background_settings.dart`、`local_notifications.dart`、`main.dart` | 授权错误可见、设置向导、前后台交接、分层测试与送达状态 |

| 服务端 | `server/internal/auth/background.go`、`connector/advisor.go`、`connector/delivery.go` | 受限授权生命周期、入库触发评估、统一事件及送达记录 |
| 新增推送模块 | 设备注册、推送适配器、outbox、回执接口 | 主手机路由、失败重试、通道健康与撤销 |

实施前需将稳定事件键与上一份去重方案统一，避免一份修复“漏发”、另一份重新制造“重发”。

## 8. 真机验收与完成标准

测试设备至少包含用户实际手机；如宣称支持多个品牌，再补各品牌代表机型。记录系统版本、应用签名与构建、网络、权限、免打扰、后台运行方式；本次没有这些现场结果。

| 场景 | 预期结果 |
| --- | --- |
| 前台、本地测试、后台端到端测试 | 能区分三个流程，各阶段状态明确 |
| 锁屏、熄屏 30 分钟及长时间待机 | 记录真实时延与系统展示情况，不用手动强制任务执行代替验收 |
| 消耗分析接口超时／500 | 已验证提醒仍可独立处理，分析错误单独显示 |
| 通知权限拒绝、渠道关闭或降级 | 精确显示阻断原因，不误报横幅成功，不循环请求授权 |
| 电脑未同步或离线 | 明确标示源数据旧，不凭旧额度编造新风险 |
| 后台授权 401、到期、设备撤销 | 停止无效重试，提示恢复方式；撤销后停止接收私有数据 |
| Wi-Fi／蜂窝切换、短暂断网 | 恢复后只处理仍有效的新事件，不补弹历史队列 |
| 系统回收进程、设备重启、覆盖安装 | 恢复授权范围内的工作与去重记录，同一事件不重复 |
| 用户强制停止 | 单独记录平台表现与恢复条件，不与普通进程回收混为一谈 |
| 推送与轮询同时到达，前后台频繁切换 | 同一事件最多一次展示；未展示原因可追踪 |
| 相同重置卡进入不同到期阶段 | 最多一次；遵守上一份降噪方案 |

建议将“服务端事件生成到系统通知提交”的推送正常网络目标设为 P95 不超过 60 秒，作为待真机验证的工程目标，不能写成已达到。源数据采集／上传延迟另计；后台轮询兜底不能声称满足此目标。分别报告有资格提醒的事件数、手机接收数、系统提交数、人工确认横幅数、延迟、重复数及跳过原因，不能把去重和免打扰的正确抑制算作漏发。

完成标准：先在真机验证第一阶段修复，再验证选定推送通道；同一事件重复展示为 0，已知失败都有可定位原因。无日志或尚未实测的机型不宣称已解决。
