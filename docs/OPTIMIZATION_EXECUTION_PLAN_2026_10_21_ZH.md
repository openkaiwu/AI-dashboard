# AI Hub 后续优化详细执行方案

日期：2026-10-21。代码基线：当前 v1.1.6 工作区。状态：待实施方案。

目标是让额度数据可信、历史可以恢复、手机提醒可追踪、监控雷达有明确依据，再扩展预算和快捷查看功能。本方案仅新增开发文档，不执行代码修改、安装或服务器发布。

## 1 交付范围和固定规则

建议分三批交付，版本号为暂定，发布时再核对实际版本与 Android 构建号。

| 批次 | 范围 | 是否依赖 Firebase | 交付条件 |
| --- | --- | --- | --- |
| A，暂定 v1.1.7 | 数据新鲜度与同步、备份恢复、提醒诊断、双端雷达统一 | 否 | 自动化回归、Windows 覆盖安装与恢复、Android 模拟器恢复验证通过 |
| B，暂定 v1.1.8 | FCM 实时通知、与定时检查共用去重、小米真机验收 | 是 | 推送项目已配置，真实手机完成约定场景与观察记录 |
| C，后续版本 | 更细消耗分析、可保存预算、手机小组件、更新中心 | 基础功能否 | A 的数据契约稳定；按功能独立验收 |

整个开发周期必须保持以下行为：

1. 桌面和网页默认静默，不因新增推送、恢复或升级重新开启额度弹窗。
2. 手机同一语义事件只主动提醒一次；重启、重新登录、恢复备份、切换主手机不清空已提醒记录。
3. 保留账号级至少 30 分钟间隔与免打扰；新通道不能绕过这些规则。
4. 快速消耗仍为最近 15 分钟至少 3 个连续有效样本、实际消耗严格超过 5 个百分点；样本间隔和最新样本不超过 3 分钟，不跨重置、账号切换或计数下降计算。
5. 默认本地保存；自动同步由用户明确开启。推送仅使用已获准同步到服务器的数据。
6. 备份不包含登录令牌、Cookie、服务账号密钥和聊天正文。恢复业务数据不恢复旧设备身份或后台授权。
7. 不同窗口不能相加；同一上游账号的多台采集设备不能被当成多份消耗。
8. 系统接受通知请求、用户看到横幅、用户点击是三个不同状态，不能混为“已读”。

## 3 阶段 A0 基线和复现

预计 1 个开发日，完成后进入数据与界面修改。

### 执行步骤

1. 记录当前 Git 差异、客户端版本、迁移编号和现有测试结果。保存代码基线快照，明确已有未提交改动，不能覆盖其他工作。
2. 对真实本地数据做只读盘点，记录文件数、大小、哈希与格式版本；使用脱敏副本开发和测试。
3. 在隔离数据库建立两台桌面、一台主手机、一台备用手机的测试场景。
4. 构造旧备份、新样本、晚到上传、重复上传、断网、缓存损坏、账号切换和重置时间修正样本。
5. 补充失败用例：旧备份遮蔽新统计、备份成功但历史写入失败、多设备重复计量。不能复现的风险保留为设计审查项，不直接宣布修复。

### 交付与验收

- 形成复现记录，包含输入、预期、实际、受影响接口。
- 测试账号与数据库同日常使用数据隔离。
- 不清空现有提醒记录，不触发真实用户通知。

## 4 阶段 A1 数据身份 新鲜度和可靠同步

预计 4 至 6 个开发日，是后续恢复、雷达和分析的基础。

### 4.1 统一数据身份

新数据至少携带以下字段；具体 JSON 名称在实现时与现有模型对齐。

| 字段 | 用途 |
| --- | --- |
| `schema_version` | 区分旧快照和新协议 |
| `provider`、`provider_account_ref` | 区分上游平台和账号，账号引用为不透明标识 |
| `identity_status` | verified、manual 或 unknown；unknown 不自动跨设备合并 |
| `source_device_id`、`collector_epoch`、`sequence` | 区分采集来源与重装后的序号空间，形成幂等上传标识 |
| `observed_at`、`received_at` | 分别表示实际采集和服务器接收时间 |
| `window_id`、`cycle_id` | 区分额度窗口和周期，不能只用可能修正的重置时间作身份 |
| `coverage_start`、`coverage_end` | 明确聚合涵盖的时间范围 |
| `quality`、`gap_intervals` | 表达连续性、缺失和来源不确定 |

先检查上游是否提供稳定账号标识。可用时转为 Hub 内部不透明引用；不得用 access token 或刷新令牌作为身份。不可用时允许用户命名并绑定采集档案，明确标为手动识别；不凭邮箱猜测、相似额度或相同重置时间合并账号。

旧记录保留为 legacy 来源。没有足够证据的旧数据不强行分摊到某个新账号，页面允许单独查看。账号识别能力不足不能阻止单设备修复，但必须阻止不可靠的跨设备汇总。

### 4.2 数据选择与统计合并

执行顺序如下：

1. 按 Hub 用户、Provider、上游账号、额度窗口分组；身份不明时再按设备隔离。
2. 使用采集时间和覆盖范围判断新旧，不使用上传时间决定业务新旧。
3. 同一账号、多设备同时观察相同额度时，选定一个有效采集源；源切换留记录，不把两台电脑的差值直接相加。
4. 能从原始样本重算的重叠区间统一重算。仅有旧聚合且来源重叠不明时，分开展示或选定来源，不直接累加。
5. 只有互不重叠且口径相同的聚合区间才允许拼接；重置、额度修正、采集空档单独标记。
6. 新响应增加 `data_as_of`、`source`、`coverage`、`stale_reason`，页面显示“数据截至某时”。

图表使用实际数据时间，不把当前响应生成时间当成采集成功时间。统一每日统计的时区，时区变更通过原始小时数据重算；旧聚合缺少重算依据时保留原时区标签。

### 4.3 可靠上传和断网补传

- 桌面增加磁盘持久化上传队列，区分待上传、已接受、待计算、失败；应用退出后队列仍保留。
- 建议单批上限 500 个样本或 512 KiB，先触及哪个就分批；这些为初始工程上限，压测后调整。
- 用来源、epoch、sequence 和内容校验形成幂等操作；同一操作重试返回同一接收结果。
- 服务端同一事务保存数据、更新接收游标和创建后续分析任务。避免“接口报错但部分成功”无法解释。
- 上传确认后再推进客户端游标。分析失败可重试，不要求客户端反复上传已经接受的样本。
- 断网重试建议采用 30 秒、1 分钟、2 分钟至最高 15 分钟退避并加入抖动；恢复网络可立即尝试，401 停止无效重试。
- 用户点击同步时显示上传阶段与计算阶段，不将“已接收”显示为“手机已看到”。
- 明确区分“仅本地”“手动同步”“自动同步”，升级不替用户开启上传。

### 4.4 改动位置

- `server/internal/connector/consumption.go`：来源选择和统计口径。
- `server/internal/connector/local_data.go`：版本化接收、事务和幂等。
- `server/internal/codex/model.go`、`server/cmd/aihub-bridge/local_store.go`：身份、采集序号、连续性。
- `apps/desktop/localData.cjs`、`apps/desktop/main.cjs`：上传队列、状态和恢复。
- `apps/web/src/LocalDataSettings.tsx`、`apps/mobile/lib/local_cache.dart`：数据时间和同步状态。
- 新数据库迁移：身份映射、上传游标、来源覆盖信息；编号实施时按当前最大编号递增。

### 4.5 验收标准

- 同一批上传重复执行 10 次，存储数量和消耗总量均不增加。
- A 电脑先上传新数据，B 电脑随后上传旧数据，最新数据时间和显示值不回退。
- 两台电脑观察同一账号，汇总消耗与选定连续样本计算结果一致，不翻倍。
- 断网 24 小时后重连，队列可继续补传；只在最后一批确认后清除对应待上传状态。
- 旧聚合无法去重时展示来源差异，不返回看似完整的错误合计。
- 快速消耗判断仍满足原阈值，补传陈旧数据不会产生迟到弹窗。

## 5 阶段 A2 本地备份和恢复中心

预计 4 至 6 个开发日，依赖 A1 的数据身份和格式版本。

### 5.1 用户界面

桌面和手机均增加“数据与备份”入口，展示：本地数据量、覆盖日期、最近成功备份、备份位置、是否存在未同步数据。

提供“立即备份”“从文件恢复”“查看备份内容”“同步设置”。桌面增加打开保存目录；手机通过系统文件选择器选定文件或目录，不要求用户输入路径。

### 5.2 备份内容和格式

使用版本化备份容器，包含清单、样本、聚合、偏好设置、数据身份映射和提醒去重历史。清单记录应用版本、格式版本、导出时间、来源范围、每个文件的长度和 SHA-256。

备份默认不含凭据或聊天。允许设置备份口令；启用加密时采用成熟库的认证加密和口令派生方案，参数与随机盐写入清单，不自创密码算法。哈希只用于完整性检查，不宣称提供文件真实性认证。

安卓使用 Storage Access Framework 选择应用私有目录之外的本地文档位置；若用户选的是云文档提供方，应显示为该提供方备份，不称为“已保存本机”。这些文档可在卸载后保留；私有应用数据不能依赖这一行为。[Android 文档存储说明](https://developer.android.com/training/data-storage/shared/documents-files)

### 5.3 恢复流程

1. 读取清单并校验格式、文件数量、总大小和哈希；限制解压规模，拒绝越界路径、软链接和不支持的未来格式。
2. 显示数据日期、账号范围、记录数量和将恢复的类别。
3. 默认合并恢复；出现身份冲突时保留两份来源，交由用户绑定，不自动覆盖现有账号。
4. 恢复前自动生成当前状态备份；暂停写入，将数据放入暂存区校验后再事务提交或原子切换。
5. 同账号的已提醒记录取并集；恢复旧备份不能删除较新的送达历史。新设备重新登录、重新注册后台授权。
6. 恢复完成后重建索引和聚合，再恢复采集与同步。导入历史默认不参与主动提醒，只从恢复后新鲜有效样本开始判定。

### 5.4 自动备份策略

- 桌面建议默认每日一次本地备份，保留最近 7 日和 4 周版本；该默认值仅在用户启用备份后生效。
- Android 选择本地目录并授权后可启用自动备份；系统未调度时显示实际成功时间，不承诺精确到点。
- 清理仅针对本应用生成、已验证存在的备份，至少保留一个有效恢复点。空间不足时保留原数据并显示失败。
- 原始历史不随备份轮换自动删除。历史压缩或清理后续单独设置。
- Windows 卸载继续默认保留；安卓文案改为“卸载前导出备份，重装后恢复”，不承诺系统提供保留按钮。[Android 存储最佳实践](https://developer.android.com/training/data-storage/use-cases)

### 5.5 改动位置和验收

改动桌面 `localData.cjs`、`preload.cjs`、`main.cjs`，Web `LocalDataSettings.tsx`，Flutter `store.dart`、`local_cache.dart`、`background_settings.dart`，以及 Android 文件选择桥接。建议新增独立备份模块，避免把解压和迁移逻辑继续堆入入口文件。

必须通过：Windows 覆盖安装后数据一致；交互卸载选择保留后重装可读；Android 导出到本地文档、卸载、重装、重新选择文件后恢复成功；损坏包和错误口令不修改当前数据；恢复旧备份不重放已提醒事件；恢复中断可回到原状态。模拟器与小米真机证据分别记录。

## 6 阶段 A3 提醒链路体检和状态修复

预计 3 至 4 个开发日，不依赖 FCM。

### 6.1 一条事件贯穿整条链路

为提醒关联以下时间点：源采集、电脑上传确认、服务器判定、手机检查或推送到达、领取提醒、系统提交、用户点击。每个阶段都携带事件 ID、批次 ID 和设备引用，不记录令牌。

主界面只展示结果和下一步，例如：

| 状态 | 用户看到的解释 | 对应操作 |
| --- | --- | --- |
| 源数据停更 | 电脑最近一次采集在 35 分钟前 | 查看采集或同步状态 |
| 等待手机检查 | 服务器已有有效提醒，手机尚未检查 | 查看后台配置 |
| 权限关闭 | 手机未允许此类通知 | 打开系统通知设置 |
| 已提醒 | 该事件已经提交过系统通知 | 查看事件，不再次弹出 |
| 免打扰或限频 | 当前暂不主动通知 | 显示原因与下一次可检查时间 |
| 提交状态不确定 | 上一次提交中断，已保留在提醒中心 | 用户自行查看，系统不自动重发 |

增加一次性的受控链路测试：产生明确标记的测试事件，不修改真实额度或真实事件收据。用户确认是否看见横幅，测试结果保存为人工反馈，不把系统 API 成功当成横幅验证。

### 6.2 送达状态与重试规则

服务端扩展现有 `mobile_reminder_receipts`，保留原唯一约束。客户端将发送阶段放入可事务更新的持久记录，避免分散标志难以恢复。

| 阶段 | 重试规则 |
| --- | --- |
| 尚未领取 | 可重复检查与唤醒 |
| 已领取且可证明未进入系统提交 | 同设备可恢复；仅在确定未发送时释放领取 |
| 已开始系统提交但未得到确定结果 | 标记不确定，禁止自动再次弹窗 |
| 系统提交成功，服务器回执失败 | 仅补传回执，不重新调用通知 API |
| 用户点击 | 记录点击，不修改送达资格 |

只有发送状态不确定并不等于发送失败。不能通过“超过 N 分钟就清除占位”恢复提醒，否则会重新引入重复弹窗。旧版已有 `reserved` 记录按保守不确定状态迁移。

网络领取响应丢失时，用稳定操作 ID 查询原结果，不生成第二次领取。关闭权限前后、切换账号前后再次校验；通知权限被拒绝本身不能消耗一个从未尝试提交的事件。

### 6.3 事件过期和限频

- 30 分钟内到来的事件等待下一次符合条件的检查，但届时必须重新验证仍然有效。
- 快速消耗若已经不满足最近 15 分钟的条件，只留历史，不在半小时后补发“正在快速消耗”。
- 额度耗尽若仍有效且数据新鲜，可以在限频结束后首次提醒；已被耗尽事件涵盖的较弱原因不再单独发送。
- 恢复网络、退出免打扰、恢复备份时均不批量补发过期事件。
- 普通重置消息、外部消息维持页面展示；同一重置卡不随紧急程度变化重复弹窗。

### 6.4 验收标准

在领取前、领取后、系统提交前后、回执上传前后分别模拟进程终止；验证重复弹窗为零，状态与可知事实一致。测试主手机切换、前后台并发、权限拒绝、授权过期与缓存损坏。账号级永久去重历史与短期诊断日志分开存储；详细诊断建议保留 7 日，送达去重记录不能随日志清理。

主要改动：`mobile_reminders.go`、`028` 后续增量迁移、`BackgroundSyncJob.kt`、`background_settings.dart`、`inbox_page.dart`、Web `Inbox.tsx`。

## 7 阶段 A4 双端监控雷达统一

预计 3 至 5 个开发日，依赖 A1，使用 A3 的链路状态。

### 7.1 统一四种判断

| 状态 | 成立条件 | 不允许的推断 |
| --- | --- | --- |
| 预计重置 | 同账号当前窗口有可信重置时间，尚未到达 | 不能说已经恢复 |
| 等待确认 | 计划时间已到，但尚无足够新样本 | 不能仅按倒计时归零修改额度 |
| 观测到恢复 | 连续有效样本显示额度回升，展示前后值与窗口证据 | 计数下降不自动等同正式重置 |
| 无法判断 | 采集空档、身份变化、样本冲突或无效时间 | 不用“没有消息”替代检查失败 |

将实际回升进一步标注为“周期变化”“疑似额度修正”“原因待确认”。要求同账号、同窗口；若账号身份未知或发生来源切换，降低判断等级或断开比较。

### 7.2 页面和交互

- 顶部显示采集、同步、外部来源三项状态，各自给出最近成功时间。
- 中部显示重置倒计时和最近额度回升；时间线可以点开前后样本和判断原因。
- 底部显示外部消息，支持搜索、72 小时筛选、来源链接和发布时间精度。
- 手机与桌面使用同样的时间过滤和状态定义；未来时间、重复 URL、来源失败的处理一致。
- 空状态分别表达“未配置”“检查失败”“过期”“筛选后为空”。

### 7.3 真正的请求检查

保留“刷新记录”用于读取已有结果，新增“请求外部检查”用于创建后台任务。任务接口返回 queued、running、completed、failed 和实际完成时间。

实施前确认外部雷达执行器位置：若现有任务在仓库外，先定义适配接口并确认可调用能力；未接通时按钮显示未配置，不能创建一个永不执行的假任务。建议初始限频每用户 5 分钟一次，同来源全局合并并发任务，最终频率按来源允许范围调整。

外部消息不能直接生成账号额度变化或主动通知，也不允许网页内容影响采集凭据或执行器配置。

### 7.4 验收标准

统一一套至少涵盖正常重置、倒计时到点未更新、短暂修正、采集空档、账号切换、未来消息时间、来源失败、重置时间修正的样本，Web 和 Flutter 输出一致。请求检查可观察真实状态；执行器不可达时显示失败并保留历史结果。

改动：`radar.ts`、`RadarPanel.tsx`、`codex_page.dart`、服务端雷达入口与任务执行适配；建议将状态判断提到服务端并输出版本化结构，客户端只负责展示和本地倒计时。

## 8 阶段 A5 回归与第一批发布

预计 2 至 3 个开发日。以上 A0 至 A5 合计约 17 至 25 个开发日，按一名开发者串行完成实现、回归和文档估算，不包含等待账号配置或不可控设备问题。

### 8.1 自动化检查

- Go：统计去重、来源选择、旧协议兼容、事务失败、回执竞态和恢复后的去重；运行相关集成测试、race 与 vet。
- Desktop：断点补传、原子写入、备份校验、恢复失败回滚、静默提醒、安装保留。
- Web：统一雷达状态、数据过期提示、同步状态与备份流程。
- Flutter 和 Android：同源测试样本、通知状态迁移、权限与生命周期、恢复文件选择、后台缓存失败独立性。
- 新旧客户端混用：旧桌面和旧手机继续可用；旧客户端不因无法识别新字段丢失原数据。

### 8.2 性能目标

以下是验收目标，均需实际测量，不是当前性能声明：

| 场景 | 初始目标 |
| --- | --- |
| 本地 10 万条额度样本统计 | 聚合查询 P95 不超过 500 ms；耗时任务不阻塞 UI |
| 首次读取本地概览 | P95 不超过 1 秒，允许先展示最后已知缓存 |
| 待上传队列恢复 | 分批处理、可取消，内存不随全部历史线性增长 |
| 普通无新事件后台检查 | 不持续保活，不额外启动前台服务 |
| 无变化的页面 | 页面不可见时降低刷新频率，恢复时检查新鲜度 |
| 雷达请求 | 同来源并发合并，避免按钮连点形成多个任务 |

基准记录设备、样本量、运行次数和 P50/P95；达不到目标时先定位瓶颈，不通过隐藏缺失数据或减少去重记录达标。

### 8.3 发布顺序与回滚

1. 保存数据库备份、服务器二进制和客户端数据备份，核对恢复可用。
2. 先部署兼容旧客户端的服务端增量迁移与 API，再发布桌面和 Android。
3. 新字段先允许空值并双读，迁移分批执行；暂不删除旧表或旧文件。
4. 使用隔离账号验证服务器健康、旧客户端访问和新客户端同步。
5. 构建最终 EXE/APK；检查版本号、Android 构建号、签名连续性和产物哈希。
6. 本机覆盖安装 EXE，验证数据、登录与采集正常；Android 单独记录模拟器与真机范围。
7. 上传版本化文件，核验后原子更新下载别名、清单和页面；下载入口继续使用项目既有的 HTTP 8888 入口，实际地址只在本机发布配置中读取。
8. 从公开下载地址完整取回两包，核对长度和整包 SHA-256，再记录发布完成。
9. 回滚优先关闭新功能并回退兼容二进制，不删除送达收据。若必须恢复旧数据库，先保护备份时间之后的送达记录；无法恢复这部分记录时暂时禁用主动通知，防止重放。

Windows 发布者签名和 Android 既有调试证书是独立发布事项。不能为“正式签名”直接更换 Android 证书导致旧包无法覆盖安装；证书迁移需单独验证并安排数据导出路径。

## 9 阶段 B FCM 实时通知和小米验收

实现预计 5 至 8 个开发日，真机验收与修复预计 3 至 5 个开发日；另安排至少 48 小时自然后台观察。上述为工作量估计，不承诺通知绝对及时。

### 9.1 外部准备

已知条件：小米手机，Google Play 服务可用，目前没有 Firebase 项目。

进入推送联调前需要：在用户管理的 Google 账号下创建 Firebase 项目，登记现有 Android 包名 `dev.aihub.aihub_mobile`，配置客户端 `google-services.json`，启用服务端发送身份并设置必要权限。服务端凭据放服务器私有配置，不打入 APK 或源码。

开发者可以先完成无配置时的兼容逻辑和测试替身；实际项目创建、授权和文件配置是外部依赖。缺少配置不阻塞 A 版本发布，界面明确显示“实时推送未配置，使用系统后台检查”。

### 9.2 服务端实现

1. 新增推送设备注册与撤销接口，绑定已认证用户和设备，保存 token 轮换信息。
2. 事件判定和待发送任务在同一事务落库，复用现有任务系统；本阶段不引入额外消息队列集群。
3. 推送只针对当前主手机、当前有效且符合免打扰和限频规则的事件。
4. 发送任务记录待发、已交给 FCM、可重试失败、永久失败和过期；重试使用稳定任务 ID。
5. 推送只携带事件或批次引用和协议版本，不携带聊天、凭据或完整分析历史。
6. 每次重试重新验证事件有效性、主手机和账号授权；token 无效时停用对应 token。

### 9.3 Android 实现

- 新增 FCM 接收入口，复用现有原生事件检查、领取、提交和回执逻辑。
- 采用应用处理的消息路径，不额外启用绕过应用去重的系统自动展示路径；前后台和定时任务竞争同一持久锁和语义收据。
- 首次注册、token 更新、重新登录时更新绑定；注销、撤销设备和主手机切换后不再允许旧设备主动提交。
- 接收入口快速处理，必要后续工作采用符合平台要求的后台任务，避免在回调里下载完整消耗分析。
- 只有需要展示的有效提醒使用高优先级。普通统计同步不使用高优先级，也不依赖推送保持进程常驻。[FCM 优先级说明](https://firebase.google.com/docs/cloud-messaging/android-message-priority)
- 保留现有周期检查；Android 周期任务由系统安排，不能把配置间隔当成精确执行时间。[JobInfo 文档](https://developer.android.com/reference/android/app/job/JobInfo.Builder)
- 推送到达并不保证横幅展示，免打扰、权限和系统限制仍按实际情况呈现。

### 9.4 小米真机测试矩阵

先记录具体机型、Android/HyperOS 版本、Google Play 服务版本、网络环境与应用设置。设置引导按实际机型验证，不写死猜测的系统入口。

| 场景 | 必须验证 |
| --- | --- |
| 前台、后台、锁屏 | 同一事件各路径竞争仍只提交一次 |
| 系统回收进程 | 可接收路径能恢复，诊断记录正确 |
| 省电模式、限制后台 | 记录实际延迟和限制，不将无法送达隐藏为成功 |
| 用户强制停止 | 不承诺自动恢复；再次打开后恢复检查和明确状态 |
| Wi-Fi 与移动网络切换 | 同一有效事件不丢失、不重复，过期事件不补弹 |
| 断网后恢复 | 仍有效事件首次提醒，已失效事件只进历史 |
| 通知或渠道关闭 | 不显示“已看到”；重新开启不重放旧提醒 |
| token 更新、账号退出、主手机切换 | 只允许当前授权主手机主动提醒 |
| FCM 与定时任务同时触发 | 系统提交次数不增加 |
| APK 覆盖更新、手机重启 | 去重记录保留，后台配置恢复 |

建议在授权正常、网络稳定的前后台场景各做至少 20 个独立测试事件，测试事件走隔离账号，不放宽真实账号 30 分钟限制。分别统计事件产生到系统提交、提交到人工观察的延迟。

以服务器已有新鲜样本为起点，初始工程目标为正常条件下推送到系统提交 P95 不超过 60 秒；未达标则根据实测调整方案，不能把该目标当成平台保证。真机缺席时该阶段不得标记验收通过。

## 11 数据和接口迁移规则

1. 迁移采用新增表和字段、双读、验证、切换的顺序。具体编号不在方案中提前占用。
2. 旧上传协议继续接受，映射为 legacy 来源；不因为缺新字段丢弃历史数据。
3. 新接口先提供能力查询。旧服务器配新客户端时显示功能不可用，不能无限重试不存在的接口。
4. 所有身份、备份、诊断、推送注册接口均以当前授权用户和设备为范围，不能信任请求体中的任意用户 ID。
5. 账号级送达记录独立于界面未读状态、备份轮换和诊断清理；迁移时保持唯一约束。
6. 手动删除业务历史与删除登录授权分开；恢复备份不悄悄开启同步或推送。
7. 数据库灾难恢复、旧客户端回退和协议降级都纳入重复提醒回归。
